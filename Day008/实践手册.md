## 1. 今日目标

今天只解决一个核心问题：

> Day007 你已经用“规则”（评分标准、词性约束、字数上限）约束模型。但模型对“关键词该长什么样”“结论该什么语气”仍有自己的理解。如果直接给它看几个“输入 → 输出”的例子，能不能比纯规则更稳？

完成后，你必须能够：

1. 说清楚 Zero-shot、One-shot、Few-shot 三者的区别与各自适用场景。
2. 用同一任务跑 Zero-shot → 1-shot → 3-shot → 5-shot，观察输出质量的边际变化。
3. 理解 Recency Bias（近因偏差）：模型更受“最后看到的示例”影响，示例顺序会影响输出。
4. 设计实验验证“示例与规则冲突时模型听谁”，建立“示例 > 规则”的工程认知。
5. 复用 Day007 的 `ReviewAnalysis` 结构化输出 + `ScoreCompleteness` 作为可量化评分工具。
6. 知道示例选择的三原则：代表性、多样性、与任务一致。
7. 讨论 Zero-shot / Few-shot / Fine-tuning 的工程选择边界（不实操 Fine-tuning）。
8. 把对比结果沉淀为“示例数 vs 输出质量”曲线，建立“何时该加示例、何时该换模型”的判断。

# 7. 先理解：Few-shot 是什么

## 7.1 Day007 已经埋下的伏笔

Day007 你已经发现：

```text
规则约束（V5 的评分标准、词性、字数）
    ↓
可复现性提升
    ↓
但“风格 / 口径”仍漂移
```

比如：

- 关键词长度：你要“续航虚标”（4 字），模型可能给“续航不符宣传”（6 字）或“续航”（2 字）
- 结论语气：你要客观陈述，模型可能加“建议商家改进”
- 评分口径：规则说“10=极度满意”，但模型对“极度”的理解与你未必一致

Few-shot 的思路：

```text
不要用规则描述“长什么样”
    ↓
直接给它看“长这样”的例子
    ↓
模型模仿，而不是理解
```

## 7.2 Zero / One / Few 的演进

```text
Zero-shot（Day007 V6）
    Prompt = 指令 + 规则 + 输入 + 输出格式
    模型靠“理解指令”做事
    优点：Prompt 短、通用、换任务不用改示例
    缺点：风格 / 口径由模型定，可能与你预期不一致

One-shot（+1 个示例）
    Prompt = 指令 + 规则 + 1 个示例 + 输入 + 输出格式
    模型靠“模仿 1 个例子”做事
    优点：风格对齐、格式稳定
    缺点：1 个示例可能不够代表性

Few-shot（+K 个示例，K 通常 2-5）
    Prompt = 指令 + 规则 + K 个示例 + 输入 + 输出格式
    模型靠“归纳 K 个例子的共性”做事
    优点：口径收敛、判断更稳
    缺点：Prompt 长、占 Token、示例选不好反而误导

Fine-tuning（改模型权重）
    用大量（几百-几万）示例更新模型参数
    优点：口径彻底对齐、推理时 Prompt 短
    缺点：要数据、要算力、要运维、不灵活
```

## 7.3 今天的方法论（四技巧）

```text
技巧 1：示例格式（Input/Output 对）
    示例 1：
    评论："xxx"
    输出：{"sentiment":"Positive",...}

技巧 2：示例数量递进（0 → 1 → 3 → 5）
    观察“质量提升的边际收益”何时归零

技巧 3：示例顺序（Recency Bias）
    同样 3 个示例，正序 vs 反序，输出可能不同
    模型更受“最后看到的示例”影响

技巧 4：示例与规则冲突
    规则说“评分 10=极度满意”
    示例里 score=10 却是负面评论
    → 模型听谁？（今天实测）
```

今天的 7 个实验，就是把这 4 个技巧**逐层叠加**到同一任务上，对比输出差异。

# 8. 实验一：Zero-shot 基线（复用 Day007 V6）

先建立“没有示例”的基线。直接复用 Day007 的 V6 Prompt（已加规则 + 分隔符），但作为今天的 Zero-shot 起点。

`Program.cs`：

```csharp
using System.ComponentModel;
using System.Text;
using System.Text.Json;
using Microsoft.Extensions.AI;
using Microsoft.Extensions.Configuration;
using OpenAI;
using System.ClientModel;

// ===== 中文控制台输入乱码修复（中文 Windows 控制台代码页 936 / GBK）=====
Encoding.RegisterProvider(CodePagesEncodingProvider.Instance);
Console.InputEncoding = Encoding.GetEncoding(936);

// ---------- 配置 ----------
IConfigurationRoot config = new ConfigurationBuilder()
    .AddUserSecrets<Program>()
    .Build();

string? model = config["DashScopeModel"];
string? key = config["DashScopeKey"];

OpenAIClientOptions clientOptions = new()
{
    Endpoint = new Uri("https://dashscope.aliyuncs.com/compatible-mode/v1")
};

IChatClient client =
    new OpenAIClient(new ApiKeyCredential(key!), clientOptions)
        .GetChatClient(model)
        .AsIChatClient();

// OpenAI 官方接口的用户改用：
// IChatClient client =
//     new OpenAIClient(key!)
//         .GetChatClient(model)
//         .AsIChatClient();

// ---------- 待分析的目标评论 ----------
string targetReview = """
    收到货第三天了，物流确实快，包装也很结实没破损。
    但是用了几天发现续航比宣传的少很多，标称10小时实际只有6小时左右。
    联系客服说是正常波动，态度倒是可以但没给解决方案。综合来看一般吧。
    """;

// ---------- Zero-shot 基线（复用 Day007 V6）----------
string zeroShot = $"""
    你是一位专业的客户体验分析师。请按以下步骤分析评论：
    1. 先识别整体情感倾向（综合考虑正面与负面因素，以核心痛点为准）
    2. 根据情感强度给出0-10评分（评分标准：10=极度满意，7=基本满意，
       5=中性/一般，3=不满意，1=极度不满）
    3. 提取3个最能代表评论主题的关键词（必须是名词或名词短语，不要动词）
    4. 用一句话总结结论（不超过20个中文字，只陈述结论不加建议）

    只输出JSON，不要任何解释。字段：sentiment、score、keywords、conclusion。

    <review>
    {targetReview}
    </review>
    """;

Console.WriteLine("===== Zero-shot 基线（0 个示例）=====");
await RunAndPrint(client, zeroShot);

// ---------- 工具函数 ----------
async Task RunAndPrint(IChatClient c, string prompt)
{
    ChatResponse<ReviewAnalysis> response =
        await c.GetResponseAsync<ReviewAnalysis>(
            prompt,
            new ChatOptions { Temperature = 0.1f, MaxOutputTokens = 400 });

    if (response.TryGetResult(out ReviewAnalysis? r))
    {
        Console.WriteLine($"  情感：{r.Sentiment}");
        Console.WriteLine($"  评分：{r.Score}/10");
        Console.WriteLine($"  关键词：{string.Join("、", r.Keywords ?? [])}");
        Console.WriteLine($"  结论：{r.Conclusion}");
        Console.WriteLine($"  完整度：{ScoreCompleteness(r)}/4");
    }
    else
    {
        Console.WriteLine($"  解析失败，原始：{response.Text}");
    }
    Console.WriteLine();
}

static int ScoreCompleteness(ReviewAnalysis r)
{
    int filled = 0;
    if (r.Sentiment != default) filled++;
    if (r.Score is >= 0 and <= 10) filled++;
    if (r.Keywords is { Count: > 0 }) filled++;
    if (!string.IsNullOrWhiteSpace(r.Conclusion)) filled++;
    return filled;
}

// ---------- 输出契约 ----------
public enum Sentiment { Positive, Negative, Neutral }

public class ReviewAnalysis
{
    [Description("情感倾向，Positive/Negative/Neutral 之一")]
    public Sentiment Sentiment { get; set; }

    [Description("0-10 情感评分，10=极度满意，1=极度不满")]
    public int Score { get; set; }

    [Description("3个关键词")]
    public List<string>? Keywords { get; set; }

    [Description("一句话结论，不超过20字")]
    public string? Conclusion { get; set; }
}
```

# 9. 实验二：One-shot（+1 个示例）

在 Zero-shot 基础上加 1 个示例。**关键是示例的输出格式要“做规矩”**——你想让模型输出什么样的风格、长度、口径，就在示例里展示什么。

```csharp
// ---------- One-shot：+1 个示例 ----------
string oneShot = $"""
    你是一位专业的客户体验分析师。请按以下步骤分析评论：
    1. 先识别整体情感倾向（综合考虑正面与负面因素，以核心痛点为准）
    2. 根据情感强度给出0-10评分（评分标准：10=极度满意，7=基本满意，
       5=中性/一般，3=不满意，1=极度不满）
    3. 提取3个最能代表评论主题的关键词（必须是名词或名词短语，不要动词）
    4. 用一句话总结结论（不超过20个中文字，只陈述结论不加建议）

    只输出JSON，不要任何解释。字段：sentiment、score、keywords、conclusion。

    示例：
    评论：物流超快，包装完好，产品非常好用，强烈推荐！
    输出：{{"sentiment":"Positive","score":9,"keywords":["物流快","包装好","产品好用"],"conclusion":"用户对物流、包装和产品都非常满意"}}

    <review>
    {targetReview}
    </review>
    """;

Console.WriteLine("===== One-shot（1 个示例）=====");
await RunAndPrint(client, oneShot);
```

### 关键改动

1. 在规则和 `<review>` 之间加了一个“示例”段。
2. 示例的输出是**手工写的标准答案**——关键词都是 3-4 字的名词短语，结论是纯陈述、15 字以内、正面。
3. 示例用 `{{...}}` 转义（C# 字符串插值中 `{{` 表示字面 `{`）。

### 观察重点

1. **关键词长度**是否向示例靠拢（从 2 字 / 6 字 → 3-4 字）？
2. **结论语气**是否更接近示例（纯陈述、无建议）？
3. **评分口径**是否被示例的“9 分 = 极度满意”校准？

### 必须得出的结论

```text
+ 1 个示例
    ↓
模型有了“长什么样”的参照
    ↓
风格 / 格式 / 口径向示例对齐
    ↓
但 1 个示例代表性不足，复杂评论可能仍漂移
```

# 10. 实验三：Three-shot（+3 个示例，覆盖三类情感）

1 个示例可能不够代表性。加到 3 个，**覆盖 Positive / Neutral / Negative 三种情感**，让模型看到“不同情感下输出长什么样”。

```csharp
// ---------- Three-shot：+3 个示例（覆盖三类情感）----------
string threeShot = $"""
    你是一位专业的客户体验分析师。请按以下步骤分析评论：
    1. 先识别整体情感倾向（综合考虑正面与负面因素，以核心痛点为准）
    2. 根据情感强度给出0-10评分（评分标准：10=极度满意，7=基本满意，
       5=中性/一般，3=不满意，1=极度不满）
    3. 提取3个最能代表评论主题的关键词（必须是名词或名词短语，不要动词）
    4. 用一句话总结结论（不超过20个中文字，只陈述结论不加建议）

    只输出JSON，不要任何解释。字段：sentiment、score、keywords、conclusion。

    示例1：
    评论：物流超快，包装完好，产品非常好用，强烈推荐！
    输出：{{"sentiment":"Positive","score":9,"keywords":["物流快","包装好","产品好用"],"conclusion":"用户对物流、包装和产品都非常满意"}}

    示例2：
    评论：东西收到了，包装完好，目前用着还行，以后再追评。
    输出：{{"sentiment":"Neutral","score":5,"keywords":["包装完好","使用体验","待追评"],"conclusion":"用户态度中性，待后续使用验证"}}

    示例3：
    评论：质量很差，用了两天就坏了，客服还不理人，非常失望。
    输出：{{"sentiment":"Negative","score":1,"keywords":["质量差","易损坏","客服失联"],"conclusion":"产品质量与售后均令用户极度不满"}}

    <review>
    {targetReview}
    </review>
    """;

Console.WriteLine("===== Three-shot（3 个示例）=====");
await RunAndPrint(client, threeShot);
```

### 示例选择三原则（今天必记）

1. **代表性**：覆盖任务可能出现的典型类别（这里覆盖了 Positive / Neutral / Negative 三类）。
2. **多样性**：示例之间要有差异（3 个正面示例不如 1 正 1 中 1 负）。
3. **一致性**：所有示例的输出格式、字段、风格必须一致（不能示例 1 有 keywords，示例 2 没有）。

### 观察重点

1. 对 `targetReview`（既有正面“物流快”又有负面“续航虚标”）的判断是否更稳？
2. 评分是否落在 3-5 区间（因为有示例 3 的“1 分=极度不满”和示例 2 的“5 分=中性”做锚点）？
3. 关键词是否更精准（如“续航虚标”“客服推诿”而不是“收到货”“综合”）？

### 必须得出的结论

```text
+ 3 个示例（覆盖三类）
    ↓
模型有了“各类情感下输出长什么样”的完整参照
    ↓
判断口径收敛、风格稳定
    ↓
这是 Few-shot 的“甜点区”
```

# 13. 实验六：示例与规则冲突时模型听谁（必做）

这是今天最重要的实验。**故意制造规则与示例的冲突**，看模型偏向谁。

场景：规则说“评分 10=极度满意”，但示例里有一条 `score=10` 却对应**负面**评论。

```csharp
// ---------- 示例与规则冲突 ----------
string conflictShot = $"""
    你是一位专业的客户体验分析师。请按以下步骤分析评论：

    只输出JSON，不要任何解释。字段：sentiment、score、keywords、conclusion。

    示例1：
    评论：质量很差，用了两天就坏了，客服还不理人，非常失望。

    输出：{{"sentiment":"Neutral","score":5,"keywords":["包装完好","使用体验","待追评"],"conclusion":"用户态度中性，待后续使用验证"}}

    示例3：

    </review>

```

### 冲突设计

- 规则：`10=极度满意，1=极度不满`
- 示例 1：Negative 评论 → `score=10`（违反规则）
- 示例 3：Positive 评论 → `score=1`（违反规则）

### 观察重点

1. 对 `targetReview` 的评分是多少？是被规则拉回（4-5），还是被示例带偏（10 或 1）？
2. 如果被带偏，说明**示例 > 规则**。
3. 如果被规则拉回，说明**规则 > 示例**（或该模型对规则更敏感）。

### 必须得出的结论

```text
大多数模型：示例 > 规则
    ↓
工程含义：
  ① 示例必须与规则一致，否则示例会覆盖规则
  ② 写示例前先复核：每个示例的输出是否符合规则？
  ③ 示例是“更强”的约束，也是“更危险”的约束
    ↓
生产代码：示例上线前要做“规则一致性校验”
```

# 14. 实验七：Zero / Few / Fine-tune 工程选择边界

今天最后一个实验是“认知实验”——不写代码，只填一张决策表。这是 Phase 6 之后 Fine-tuning 实操前的预认知。

### 决策矩阵

| 场景 | Zero-shot | Few-shot | Fine-tuning |
|---|---|---|---|
| 简单分类（情感正/负） | ✅ 首选 | 可加 1-2 个 | ❌ 杀鸡用牛刀 |
| 复杂结构化输出（多字段） | 先试 | ✅ 3-5 个 | 数据多再考虑 |
| 风格对齐（语气 / 口吻） | 难 | ✅ 首选 | 数据多更好 |
| 领域术语（医疗 / 法律） | 难 | 中 | ✅ 更好 |
| 输出格式严格（JSON Schema） | ✅ 配合 Schema | 可加示例 | ✅ |
| 任务固定 + 海量调用 | ✅ Prompt 短 | 可 | ✅ 降本 |
| 任务多边 / 快速迭代 | ✅ 最灵活 | ✅ 灵活 | ❌ 不灵活 |
| 数据量 < 100 条 | ✅ | ✅ | ❌ 不够 |
| 数据量 100-1000 | ✅ | ✅ 首选 | 可试 |
| 数据量 > 10000 | - | - | ✅ 首选 |

### 选择流程

```text
Step 1：先试 Zero-shot（+ Day007 的规则约束）
    ↓ 满足要求 → 用
    ↓ 不满足 → Step 2

Step 2：加 Few-shot（2-5 个示例）
    ↓ 满足要求 → 用
    ↓ 不满足 → 判断原因
        ① 示例选不好 → 换更典型示例
        ② 任务太复杂 → 拆子任务（Day007 分步推理）
        ③ 模型能力不足 → 换更强模型
        ④ 以上都不是 → Step 3

Step 3：Fine-tuning
    前提：数据 > 1000 条、任务固定、投入产出比划算
    成本：数据标注 + 训练算力 + 运维 + 不灵活
    收益：Prompt 短、口径彻底对齐、推理成本可能降低
```

### 必须记住的边界

```text
Few-shot 改的是 Prompt（输入）
Fine-tuning 改的是模型权重（参数）
    ↓
Few-shot：灵活、零数据门槛、但占 Token
Fine-tuning：固化、要数据、但推理时 Prompt 短
    ↓
工程默认路径：Zero → Few → Fine
不要跳过 Few 直接 Fine，除非你确认数据足够且任务固定
```

# 15. 六个实验对比总结

把今天的核心结论浓缩成一张表：

| 实验 | 加了什么 | 解决什么问题 | 仍可能存在的问题 |
|---|---|---|---|
| 实验一 Zero-shot | （基线，Day007 V6） | 无 | 风格 / 口径漂移 |
| 实验二 One-shot | +1 示例 | 风格对齐 | 1 个不够代表性 |
| 实验三 Three-shot | +3 示例（覆盖三类） | 口径收敛 | 示例选不好仍误导 |
| 实验四 Five-shot | +5 示例 | 几乎无边际收益 | Token 浪费 |
| 实验五 反序 | 示例顺序对调 | 揭示 Recency Bias | 顺序影响输出 |
| 实验六 冲突 | 示例与规则打架 | 揭示“示例 > 规则” | 示例必须与规则一致 |

工程上的 Few-shot 进化路径：

```text
Zero 能用 → One 对齐风格 → Three 稳口径 → Five 边际递减
                                            ↓
                                        考虑换模型 / Fine-tune
```

> 注意：不是所有任务都需要 Few-shot。Zero-shot + 良好规则（Day007 V6）对很多任务已经够用。Few-shot 是“Zero 不够稳时的增强”，不是“默认配置”。

```csharp
    输出：{"sentiment":"Negative","score":2,"keywords":["电池衰减","客服推诿","售后差"],"conclusion":"产品耐久性与售后均令用户不满"}
    """;

// ---------- 6 个变体 ----------
(string Name, string Prompt)[] variants =
[
    ("Zero-shot",   $"{rules}\n\n<review>\n{targetReview}\n</review>"),

    ("One-shot",    $"{rules}\n\n{exPositive}\n\n<review>\n{targetReview}\n</review>"),

    ("Three-shot",  $"{rules}\n\n{exPositive}\n\n{exNeutral}\n\n{exNegative}\n\n<review>\n{targetReview}\n</review>"),

    ("Five-shot",   $"{rules}\n\n{exPositive}\n\n{exNeutral}\n\n{exNegative}\n\n{exNeutral2}\n\n{exNegative2}\n\n<review>\n{targetReview}\n</review>"),

    ("Three-reversed", $"{rules}\n\n{exNegative}\n\n{exNeutral}\n\n{exPositive}\n\n<review>\n{targetReview}\n</review>"),

    ("Conflict",    $"{rules}\n\n" +
     $"示例：\n评论：质量很差，用了两天就坏了，客服还不理人，非常失望。\n" +
     $"输出：{{\"sentiment\":\"Negative\",\"score\":10,\"keywords\":[\"质量差\",\"易损坏\",\"客服失联\"],\"conclusion\":\"产品质量与售后均令用户极度不满\"}}\n\n" +
     $"{exNeutral}\n\n" +
     $"示例：\n评论：物流超快，包装完好，产品非常好用，强烈推荐！\n" +
     $"输出：{{\"sentiment\":\"Positive\",\"score\":1,\"keywords\":[\"物流快\",\"包装好\",\"产品好用\"],\"conclusion\":\"用户对物流、包装和产品都非常满意\"}}\n\n" +
     $"<review>\n{targetReview}\n</review>"),
];

// ---------- 逐个跑变体 ----------
Console.WriteLine($"测试评论：{targetReview}");
Console.WriteLine(new string('=', 60));
Console.WriteLine();

foreach (var (name, prompt) in variants)
{
    Console.WriteLine($"===== {name} =====");
    ChatResponse<ReviewAnalysis> response =
        await client.GetResponseAsync<ReviewAnalysis>(
            prompt,
            new ChatOptions
            {
                Temperature = 0.1f,
                MaxOutputTokens = name == "Five-shot" ? 500 : 400
            });

    if (response.TryGetResult(out ReviewAnalysis? r))
    {
        Console.WriteLine($"  情感：{r.Sentiment}");
        Console.WriteLine($"  评分：{r.Score}/10");
        Console.WriteLine($"  关键词：{string.Join("、", r.Keywords ?? [])}");
        Console.WriteLine($"  结论：{r.Conclusion}");
        Console.WriteLine($"  完整度：{ScoreCompleteness(r)}/4");
    }
    else
    {
        Console.WriteLine($"  解析失败，原始：{response.Text}");
    }
    Console.WriteLine();
}

// ---------- 工具函数 ----------
static int ScoreCompleteness(ReviewAnalysis r)
{
    int filled = 0;
    if (r.Sentiment != default) filled++;
    if (r.Score is >= 0 and <= 10) filled++;
    if (r.Keywords is { Count: > 0 }) filled++;
    if (!string.IsNullOrWhiteSpace(r.Conclusion)) filled++;
    return filled;
}

// ---------- 输出契约 ----------
public enum Sentiment { Positive, Negative, Neutral }

public class ReviewAnalysis
{
    [Description("情感倾向，Positive/Negative/Neutral 之一")]
    public Sentiment Sentiment { get; set; }

    [Description("0-10 情感评分，10=极度满意，1=极度不满")]
    public int Score { get; set; }

    [Description("3个关键词")]
    public List<string>? Keywords { get; set; }

    [Description("一句话结论，不超过20字")]
    public string? Conclusion { get; set; }
}
```

# 20. troubleshooting.md

创建 `Day008/troubleshooting.md`，模板：

```markdown
# Day008 Troubleshooting

## 问题 1：Few-shot 输出和 Zero-shot 几乎一样

### 现象
加了 3 个示例，输出和 Zero-shot 没区别。

### 原因
1. 模型能力太强，Zero-shot 已经做对。
2. 任务太简单，示例无增益。
3. 示例与规则一致，没有新信息。

### 解决
1. 换一条更复杂的测试评论（既有正面又有负面、核心痛点不明显）。
2. 故意把示例写得更“苛刻”（如关键词都是 4 字名词短语），看模型是否对齐。
3. 这本身是有效结论——说明该任务 Zero 已够用。

---

## 问题 2：Five-shot 解析失败（TryGetResult=false）

### 现象
加到 5 个示例后反而解析不出结构化结果。

### 原因
1. Prompt 太长，挤占了 MaxOutputTokens（输出被截断）。
2. 示例的 JSON 格式与 Schema 不一致（如示例里有 `score` 但类型是字符串）。
3. 模型把示例的 JSON 当成“要重复的模板”，输出了一段示例式的多 JSON。

### 解决
1. MaxOutputTokens 提到 500+。
2. 检查示例 JSON 的字段名 / 类型与 `ReviewAnalysis` 一致。
3. 在 Prompt 里明确“只输出一个 JSON 对象，不要输出示例”。

---

## 问题 3：Conflict 实验模型仍听规则（score 没被带偏）

### 现象
示例里 score=10 是负面，但模型对 targetReview 仍给 4 分（听规则）。

### 原因
1. 模型对规则文字更敏感（部分新模型倾向遵守显式规则）。
2. 示例冲突不够明显（如只冲突 1 个字段）。

### 解决
1. 记录“该模型规则 > 示例”——这是宝贵数据。
2. 多跑几次确认稳定性。
3. 不要因此认为“示例没用”——换个模型可能结论相反。

---

## 问题 4：示例的 JSON 转义出错

### 现象
Prompt 里写示例的 JSON，运行时 C# 字符串插值报错或 JSON 解析失败。

### 原因
C# 字符串插值（$"..."）中 `{` 是特殊字符，要写 `{{` 才表示字面 `{`。

### 解决
1. 用 `$"""..."""` 原始字符串插值，`{{` 表示 `{`。
2. 或用 `string.Concat` / `StringBuilder` 拼接，避免插值。
3. 示例 JSON 的 `{` `}` 全部双写。

---

## 问题 5：Recency Bias 不明显

### 现象
Three-shot 正序和反序输出几乎一样。

### 原因
1. 模型对示例顺序不敏感（部分新模型已优化）。
2. 3 个示例差异不够大（都是同类情感）。

### 解决
1. 换差异更大的示例（如 1 正 1 中 1 负，正反序差异才明显）。
2. 记录“该模型无显著 Recency Bias”——也是有效结论。
```

# 27. Day008 → Day009 的衔接

Day008 你已经发现：

```text
Few-shot 的痛点
    ↓
示例段写死在 Prompt 字符串里
    ↓
换任务 / 换模型 / 换示例 → 改代码 → 重新部署
    ↓
不灵活、不复用、难版本管理
```

比如今天你写了 5 个示例，明天想：
- 换 3 个更典型的示例 → 改 Program.cs
- 按输入动态选示例（Dynamic Few-shot）→ 没法用静态字符串
- 给不同用户用不同示例集 → 没法配置化
- 给示例做 A/B 测试 → 没法版本管理

Day009 学：

> **Prompt 模板与复用**

```text
Day008：示例写死在 Prompt 字符串里
Day009：把 Prompt 抽成模板，示例 / 角色 / 规则 / 输入都用变量注入
    ↓
Prompt 成为“可配置、可版本化、可复用”的资产
```

对比预告：

```text
Day008 写法（硬编码）：
    string prompt = $"你是分析师。规则：…示例：…评论：{review}";
    → 改任何一段都要改代码

Day009 写法（模板化）：
    var template = new PromptTemplate("你是{{role}}。规则：{{rules}}示例：{{examples}}评论：{{input}}");
    var prompt = template.Render(new { role = "分析师", rules = ..., examples = ..., input = review });
    → 模板与数据分离，示例可配置化、可版本化
```

今天的 6 个变体（Zero/One/Three/Five/Reversed/Conflict），在 Day009 会变成“同一模板 + 不同示例配置”的渲染结果——代码量大减，可维护性大增。

再回答：

> **“示例与规则冲突时模型听谁？你怎么防？”**

```text
多数模型：示例 > 规则
    ↓
工程对策：
  ① 示例上线前做“规则一致性校验”
```
